# Shura ProComic repository (separate, NOT PUBLISHED)

**Status: staged for review only. Nothing here has been published, pushed or
uploaded anywhere.**

## Why this is a separate tree

ProComic is signed by a different certificate than the 72 Keiyoushi extensions in
`/workspace/repo`:

| repository | advertised `signingKeyFingerprint` | count |
|---|---|---|
| `/workspace/repo` (existing, live) | `9add655a78e96c4ec7a53ef89dccb557cb5d767489fac5e785d671a5a75d4da2` (Keiyoushi) | 72 |
| this tree | `b655a474503f4471fdaf6ba35b9385f71d144669f3c28602c5b60b062022c41d` (LoneVertex) | 1 |

Mihon trusts **one** key per repository. Mixing the two in one tree means the
`repo.json` anchor can only name one of them, and a reader that anchors on the
other refuses to install. This tree therefore carries only the LoneVertex key
and only the ProComic artifact, so the anchor is unambiguously correct.

The 72-extension tree at `/workspace/repo` is **not** modified by this work.

## Verify before publishing

```

```

Re-derives the APK digest against the upstream release `.sha256`, re-runs
`aapt2`, re-runs `apksigner verify --print-certs --verbose`, decodes `index.pb`
and checks every index file against every other one. 26 checks, all passing.

## Known gap: extension_lib

`index_pb._extension_message()` derives `extension_lib` from the version string
(`1.5.1` → `1.5`). This APK's own `AndroidManifest.xml` declares:

```xml
<meta-data android:name="tachiyomix.extensionLib" android:value="1.6" />
```

`1.5` is inside Mihon's supported range, and Shura's `ExtensionLoader` reads
`1.6` from the manifest and accepts it (`ApkManifestReader.kt`, range
`1.0..1.6` in `ExtensionLoader.kt:67`). Left as-is rather than patched, because
the encoder has no override hook and all 72 Keiyoushi entries already publish
`1.6` for the same reason (their versions are `1.6.x`). Raise it if you want the
index to state 1.6.

## Site behaviour that the operator should know about

The site is **not** JavaScript-rendered and **not** login-walled for reading.
Verified live on 2026-10-16:

* Catalogue is a public JSON API (`/api/public/content/popular-new`,
  `/latest-updates`, `/series/search`), all HTTP 200 unauthenticated.
* Chapter lists are `/api/chapters?contentId=` , HTTP 200 unauthenticated.
* The reader page is server-rendered HTML containing an `appImages` JSON
  manifest. A plain `GET` returns it; no browser is involved.
* `POST /chapter-map-proxy-plan/{chapterId}` returns the signed tile plan for the
  watermarked pages, HTTP 200, with no cookies and no token beyond the one the
  reader page already handed out.

Two real limitations, neither of which is JavaScript:

1. **Coin/shortlink-locked chapters.** Roughly a third of chapters are locked;
   the extension refuses them by design with
   `الفصل مقفل ويتطلب عملات على الموقع`. Those are a site-side paywall, not a
   fetch failure.
2. **Only ~3 of a chapter's pages are direct image URLs.** The rest are
   watermarked and served as signed AVIF tile grids that the extension
   reassembles on-device with `android.graphics` + `libavif_android.so`. The
   signed tiles themselves download fine unauthenticated (verified), but the
   final canvas stitch can only run on a device. A chapter that returns 17 pages
   therefore gives 3 direct images and 14 tile-reconstructed ones.
